# Approval request system — LemmaScript model

A model of [`../spec.md`](../spec.md) written in [LemmaScript](https://lemmascript.org/): annotated TypeScript that
`lsc` compiles to Dafny and verifies there. The program (`approval.ts`) is a runnable TypeScript module, the
`//@ requires` / `//@ ensures` / `//@ invariant` annotations are the specification, and the proof obligations are
discharged by Dafny on the generated code. The same source is therefore, at once, an executable reference
implementation (`scenarios.ts` runs it under Node.js) and a proved model of the access rules and of P1–P3.

The second half of this document compares the model with the direct Dafny model in [`../dafny/`](../dafny/), which
proves the same properties without going through TypeScript.

| File | Role |
| --- | --- |
| `approval.ts` | The model: directory, states, access rules, transitions, trace, `Workflow` class — with contracts |
| `approval.dfy.gen` | Dafny generated by `lsc gen`. **Never edited by hand**; regenerated from `approval.ts` |
| `approval.dfy` | The proof-owned copy: `approval.dfy.gen` plus *additions only* — loop invariants, `modifies`, the P1–P3 lemmas |
| `scenarios.ts` | The tables of `spec.md` executed under Node.js on the very TypeScript that was verified |
| `negative/*.dfy` | Claims that must **not** verify; CI requires them to fail |
| `checks.json` | The list of checks run by `scripts/lemmascript.py` and by CI |

## Running from the CLI

Requirements: Python 3.11+, Node.js 22.18+ or 24+ (with npm; `scenarios.ts` relies on the built-in type stripping) and
Dafny 4.11.0. The driver downloads Dafny into `.tools/dafny-4.11.0/` through `scripts/dafny.py` and installs the
LemmaScript CLI (`lemmascript@0.6.1`) into `.tools/lemmascript/` on first use, unless an `lsc` of that version is
already on `PATH` (or given via `LSC_BIN`).

```sh
$ make verify-lemmascript                                  # every */lemmascript directory
$ ./scripts/lemmascript.py verify approval_request/lemmascript
ok   check                               approval.dfy.gen regenerated, 41 proof obligation group(s) verified (2.5s)
ok   scenarios                           8/8 scenarios passed (0.1s)
ok   negative-authority-leak             as expected, 1 verification error(s), 0 verified (1.3s)
ok   negative-directory-without-manager  as expected, 2 verification error(s), 0 verified (1.1s)
ok   negative-author-edits-pending       as expected, 1 verification error(s), 0 verified (1.1s)

5/5 checks passed
```

The checks come from `checks.json`. `"kind": "check"` runs `lsc check --backend=dafny`, which regenerates
`approval.dfy.gen`, confirms that `approval.dfy` is additions-only over it, and verifies `approval.dfy`; the driver
also fails if the committed `approval.dfy.gen` was stale. `"kind": "run"` executes the scenarios with Node.js.
`"kind": "verify"` runs `dafny verify` on a file, and `"expect": "violation"` turns a verification failure into the
expected result.

```sh
$ ./scripts/lemmascript.py checks approval_request/lemmascript                     # list the checks
$ ./scripts/lemmascript.py verify approval_request/lemmascript --only check        # one check
$ ./scripts/lemmascript.py trace  approval_request/lemmascript --only negative-authority-leak   # full Dafny output
$ ./scripts/lemmascript.py run    approval_request/lemmascript                     # the scenarios, verbosely
$ ./scripts/lemmascript.py lsc -- version                                          # the LemmaScript CLI itself
$ ./scripts/lemmascript.py dafny -- verify approval_request/lemmascript/approval.dfy
```

### Editing the model

`approval.dfy` carries proof additions, so after changing `approval.ts` do not delete and regenerate it; run

```sh
$ ./scripts/lemmascript.py lsc -- regen --backend=dafny approval_request/lemmascript/approval.ts
```

which regenerates `approval.dfy.gen` and three-way merges the additions into the new code (`lsc regen` leaves an
`approval.dfy.base` behind if the merge fails; remove it and retry once the conflict is resolved). Proof additions go
to `approval.dfy` only — the generated lines must not be modified or removed, and `//@ assume` is not used anywhere.

## Structure of the model

| Spec (`spec.md`) | In the model |
| --- | --- |
| Users / departments | `type UserId = string`, `type DepartmentId = string` (aliases; no non-emptiness constraint, see the comparison) |
| Affiliation and role `(user, department) -> role` | `interface Directory { roles: Map<UserId, Map<DepartmentId, Role>> }`. Per user, a map from department to role; a `Map` key has one value, so "one role per affiliation" needs no invariant |
| Every department has a Manager (premise of P3) | `hasManager` / `departmentsHaveManagers`: `//@ pure` functions whose body is a loop. They run under Node.js and are usable inside `//@ ensures`; `approval.dfy` supplies the quantifier they are proved equal to |
| Request states | Discriminated union `Status = { kind: "Draft" } \| { kind: "Pending" } \| { kind: "Returned"; returnedBy } \| { kind: "Approved"; approvedBy } \| { kind: "Rejected"; rejectedBy }`. Only decisions carry the decider |
| State diagram | `edit` / `submit` / `approve` / `reject` / `returnToAuthor`: total functions guarded by `//@ requires canEdit(...)` etc. "Approve a Draft" is not a runtime denial but a program that does not verify |
| Postconditions | `//@ ensures` — the frame of each transition (`\result.status === r.status && \result.author === r.author ...`) |
| Read / edit / submit / decide permissions | `canRead` / `canEdit` / `canSubmit` / `canDecide`, each with `//@ ensures` that pin the rule (`canDecide` ⇔ Pending ∧ Manager of the *target* department). U2 is the `ensures` "neither author nor manager ⇒ cannot edit" |
| Arbitrary (state, command) from outside | `step(dir, actor, r, cmd): Outcome`, with `Outcome = Success \| Failure(denial)` and a `Denial` union naming the reason. Total; classifies then delegates to the guarded transitions |
| Traces | `run(dir, r, events)` folds `step` over an array; `//@ invariant` lifts the one-step `ensures` of `step` to identity immutability and P2 along any trace |
| A system holding many requests | `class Workflow` with `requests: Map<number, Request>`. The class invariant (every stored request is well-formed) is stated as `//@ requires` / `//@ ensures` of `open` and `apply`, so it is preserved by any sequence of calls |
| P1–P3 | One-step versions are `//@ ensures` of `step` in `approval.ts`. The named theorems (`NoAuthorityLeakAcrossDepartments`, `TerminalRequestsRejectEveryCommand`, `EveryPendingRequestHasADecider`, `PendingRequestsCanBeDecided`, `WorkflowHasNoOrphanedRequests`) are proof additions in `approval.dfy` |
| Scenarios | `scenarios.ts`: eight named runs of the TypeScript itself (`node scenarios.ts`) |
| Intent | `//@ contract` sentences on the access rules and transitions — natural-language metadata for readers and agents, not proof obligations |

### What made it LemmaScript-like

- **One source, two readers.** `approval.ts` is imported unchanged by `scenarios.ts` and executed by Node.js; the
  same file is compiled by `lsc` and its contracts are proved by Dafny. There is no reference implementation to keep
  in sync with the model — the model *is* the implementation.
- **Discriminated unions are Dafny datatypes.** `Status`, `Command`, `Outcome` are `{ kind: ... }` unions and become
  `datatype Status = Draft | Pending | Returned(returnedBy: UserId) | ...`. A `switch (cmd.kind)` becomes a `match`,
  and narrowing (`if (outcome.kind === "Success") outcome.value`) becomes a destructor guarded by `Success?`.
- **`//@ pure` for loops that specifications need.** `hasManager` and `departmentsHaveManagers` iterate over the
  `Map`s; marked `//@ pure` they are emitted as Dafny `function ... by method`, so `//@ ensures` clauses and the
  P3 lemmas can mention them while Node.js runs the loops.
- **Preconditions carry the permissions.** `approve` has `//@ requires canDecide(dir, actor, r)`. Whoever calls it —
  `step`, or a future caller in another module — has to establish the permission, and Dafny checks that at every call
  site. `step` is the single place where the permission is *tested* rather than *assumed*.
- **Frames as `ensures`.** Each transition states not only what changes but what does not
  (`\result.author === r.author && \result.department === r.department && \result.content === r.content`), which is
  what makes identity immutability provable along any trace without an inductive argument in the model.
- **Loop invariants where TLA+ would have a model checker.** `run` has `//@ invariant current.author === r.author`
  and `//@ invariant isTerminal(r.status) ==> current === r`; Dafny proves them once, for traces of any length and
  directories of any size.
- **Classes with contracts for the mutable shell.** `Workflow.open` / `Workflow.apply` state the store invariant as
  `forall(id, this.requests.has(id) ==> wellFormed(this.directory, this.requests.get(id)))` in `requires` and
  `ensures`. The `modifies this` clauses Dafny needs for heap updates are one-line proof additions in `approval.dfy`.
- **Negative checks.** `negative/*.dfy` include `approval.dfy` and state claims that must fail: a manager of another
  department deciding (P1), P3 without `departmentsHaveManagers`, approving a Draft, the author editing a Pending
  request (U1/U3). Widening `canEdit` by mistake makes `negative-author-edits-pending` verify and CI turns red.

## Comparison with the direct Dafny model (`../dafny/`)

Both models prove the same statements — P1, P2 (one step and along any trace), P3 (existence of a decider and of a
terminal successor), the access rules R/U/C/D–F, identity immutability, well-formedness preservation — and both have
no scope: they hold for any number of users, departments and steps. Both keep a `negative/` directory and a
`checks.json`, run through the same kind of `scripts/*.py` driver. The differences are in *where* the specification
lives, *what* the type system can carry, and *how much* of the proof text is written by a human.

### Where the specification lives

| | Direct Dafny (`Approval.dfy` etc.) | LemmaScript (`approval.ts` + `approval.dfy`) |
| --- | --- | --- |
| Source of truth | Five Dafny modules (`Approval`, `Properties`, `Workflow`, `Scenarios`, `Demo`) | One TypeScript file; `approval.dfy` is derived from it plus additions |
| Executable form | `dafny run` / `dafny test` compile to Python | `node scenarios.ts` runs the TypeScript directly, no compilation |
| Specification syntax | Dafny `requires` / `ensures` / `invariant` / `ghost` | `//@ requires` / `//@ ensures` / `//@ invariant` inside TypeScript, `\result`, `forall(x, ...)`, `===` |
| Proof text | All by hand: `Properties.dfy` (200 lines), `calc`, `:|`, induction over `|events|` | Generated for everything stated in `.ts`; under 80 hand-written lines of additions for invariants, `modifies` and the named lemmas |
| Who reads it | Someone who knows Dafny | A TypeScript reader can follow the program and most of the contracts; Dafny knowledge is needed for the additions and for reading verification errors |

Concretely, the direct model states "a decided request is frozen along any trace" as a lemma proved by induction:

```dafny
lemma TerminalRequestsAreFrozen(dir: Directory, r: Request, events: seq<Event>)
  requires Terminal(r.status)
  ensures Run(dir, r, events) == r
  decreases |events|
{ /* recursion on events[1..] */ }
```

### What the type system carries

| Constraint | Direct Dafny | LemmaScript |
| --- | --- | --- |
| Non-empty identifiers | Subset types `type UserId = s: string \| s != "" witness "u"` | Plain `string` aliases; no constraint. `spec.md` does not require one, so the model does not check it |
| Non-empty title, non-negative amount | Subset types `Title` / `Amount`: an invalid `Content` **cannot be constructed** | Runtime predicate `validContent(c)`, tested by `create` (denial `InvalidContent`) and recorded in its `ensures` |
| Every department has a Manager | `type Directory = a: Assignment \| DepartmentsHaveManagers(a) witness ...`: a managerless assignment **is not a `Directory`**, so no predicate or lemma restates the premise | `Directory` is a record; `departmentsHaveManagers(dir)` is a `//@ pure` function. P3 lemmas carry it as `requires` — and `negative/DirectoryWithoutManager.dfy` shows the lemma fails without it |
| Key of the assignment | `map<(UserId, DepartmentId), Role>` — a pair-keyed map | `Map<UserId, Map<DepartmentId, Role>>` — nested maps (TypeScript `Map` keys are compared by identity, so a tuple key does not work at runtime) |
| Request identifiers | `nat` | `number` (a nominal alias for `number` collided with the generated `map<int, ...>` and was dropped) |

This is the largest modelling difference. Dafny's subset types move well-formedness into the *type*, so it is
established once at construction and never restated; LemmaScript's types are TypeScript's, so well-formedness is a
*predicate* that has to be assumed (`requires`) or established (`ensures`) wherever it matters. The LemmaScript
version therefore has to say `requires departmentsHaveManagers(dir)` on P3, and the `create` transition has to test
`validContent` at runtime — which is exactly what a TypeScript service would do, and what the Dafny version cannot
express because the invalid value does not exist there.

### How the transitions are shaped

| | Direct Dafny | LemmaScript |
| --- | --- | --- |
| Guarded transitions | `function Approve(...) requires CanDecide(...)` | `approve(...)` with `//@ requires canDecide(...)` — same shape |
| Dynamic entry point | `Step(...): Outcome<Request>`, a *failure-compatible* type (`IsFailure` / `PropagateFailure` / `Extract`), so `Workflow` writes `var next :- Step(...)` | `step(...): Outcome`, a plain discriminated union; `Workflow.apply` tests `outcome.kind === "Success"` |
| Denial reasons | `datatype Denial` — the same idea | `type Denial = "NotAffiliated" \| "NotAuthor" \| ... \| "NoSuchRequest"`, a string-literal union that becomes a Dafny datatype |
| Store | `class System` with `ghost var history` and `ghost predicate Valid()` | `class Workflow` without ghost state; the invariant is spelled out as a `forall(...)` in each method's `requires` / `ensures` |
| Mutation | `requests := requests[id := next]` | `const stored = new Map(this.requests); stored.set(id, ...); this.requests = stored;` — an in-place `this.requests.set(...)` is lowered by `lsc 0.6.1` to an invalid nested update, so the model copies the map |

`ghost` is the feature the LemmaScript model misses most. The direct model keeps a specification-only `history`
sequence and refers to it from `Scenarios.dfy` (`assert system.history == [...]`); LemmaScript has no ghost state,
so the trace theorems are stated over the pure `run` function instead of over the class.

### How the proofs are produced

| | Direct Dafny | LemmaScript |
| --- | --- | --- |
| Lemma for each `ensures` | Written by hand in `Properties.dfy`, one lemma per rule | Generated: `lsc` emits `isManagerOf_ensures`, `canEdit_ensures`, `step_ensures`, ... as lemmas next to the functions (`approval.dfy.gen`) |
| Named theorems P1–P3 | `Properties.dfy` | Proof additions at the end of `approval.dfy` (six lemmas); the existence proofs pick witnesses with `:|` exactly as the direct model does |
| Loops | `Run` is recursive, so no loop invariants; induction is explicit in the lemmas | `run`, `hasManager`, `departmentsHaveManagers` are loops; `//@ invariant` in the `.ts` where the invariant is stateable in TypeScript, additional invariants in `approval.dfy` where it needs `i_user_keys[j]`-style variables that only exist after lowering |
| Specification-side bodies of `//@ pure` loops | n/a — Dafny `predicate`s are written directly as quantifiers | The generated `function by method` has no function body; `approval.dfy` adds `exists user <- dir.roles.Keys :: isManagerOf(dir, user, dep)` (and the `forall` for `departmentsHaveManagers`) and Dafny proves the loop computes it |
| Frame conditions | `modifies this` on `System` methods | `modifies this` added in `approval.dfy` (LemmaScript 0.6.1 does not emit it) |
| Verification workload | 5 files, `dafny verify` + `dafny test` + `dafny run` | 41 proof-obligation groups in `approval.dfy`, verified through `lsc check`; scenarios run under Node.js instead of `dafny test` |

### Trust boundary

- The direct model trusts Dafny and the Dafny-to-Python compiler for `dafny run` / `dafny test`.
- The LemmaScript model trusts Dafny **and `lsc`**: the claim "the TypeScript satisfies the contracts" holds insofar
  as `approval.dfy.gen` faithfully reflects `approval.ts`. The generated file is committed and diffable, `lsc check`
  fails if `approval.dfy` deviates from it other than by additions, and `scenarios.ts` exercises the TypeScript
  itself — but the equivalence between the TypeScript semantics and the generated Dafny is the compiler's, not the
  verifier's. Two LemmaScript 0.6.1 behaviours steered the model (an in-place `Map.set` on a field, a nominal `number`
  alias) and are recorded above so a future version can lift them.
- Cross-module calls would be emitted as `function {:axiom}` by `lsc`; the model avoids that by living in one file.

### Summary

The direct Dafny model is the stronger *specification*: subset types make invalid directories, titles and amounts
inexpressible, `ghost` state and failure-compatible types keep the specification out of the executable code, and the
proofs are written where they are read. The LemmaScript model is the stronger *implementation*: the proved program is
ordinary TypeScript that runs unchanged, its access rules and frame conditions are contracts on the functions a
service would actually call, and most of the lemma text is generated. On this problem the two prove the same
theorems; the trade is Dafny's type-level invariants and ghost state against LemmaScript's single-source,
directly-executable model with a compiler in the trusted base.
