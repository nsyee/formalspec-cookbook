`@approval_request`
# 機能: 稟議申請システム (Approval Request Workflow)

兼務（複数部署への同時所属）を前提とした稟議申請のワークフローと、その権限モデル。
対象の自然言語仕様は [`../spec.md`](../spec.md)。

## 構成要素

| 構成要素 | このモデルでの表現 |
| --- | --- |
| 部署 (Department) | 名簿の表の `部署` 列に現れる名前 |
| ユーザー (User) | 名簿の表の `ユーザー` 列に現れる名前 |
| 所属と役職 (Affiliation) | 名簿の 1 行 = (ユーザー, 部署, 役職)。役職はユーザー単体ではなく **組** に付く |
| 稟議申請 (Request) | 作成者・申請先部署・状態（と内容）を持つレコード。各シナリオは原則 1 件の申請を扱う |

## 状態モデル

`spec.md` §2 の状態機械。終端状態（✓）からはいかなる操作でも遷移しない（ルール「P2」を参照）。

```
            提出                   承認
  Draft ─────────────▶ Pending ─────────────▶ Approved ✓
    ▲                   │  │      却下
    │                   │  └─────────────────▶ Rejected ✓
    │          差し戻し │
  Returned ◀────────────┘
    │  提出（再提出）
    └────────────────▶ Pending
```

## 背景: 兼務を含む名簿

すべてのシナリオは同じ名簿の上で動く。`carol` が **sales の一般メンバーかつ eng の上長** である点が、
このお題の中心（P1）を突くための配置である。`dave` は eng にしか所属していない。

* 前提 名簿が次の通りである:
  | ユーザー | 部署  | 役職    |
  | -------- | ----- | ------- |
  | alice    | sales | Member  |
  | bob      | sales | Manager |
  | carol    | sales | Member  |
  | carol    | eng   | Manager |
  | dave     | eng   | Member  |
* かつ すべての部署に上長が 1 名以上いる

## ルール: 申請は、作成者が所属する部署にしか作れない (A)

`spec.md` §4-A。事前条件は「実行者が申請先部署に所属していること」、事後条件は
「状態 `Draft`、作成者 = 実行者、申請先 = 入力された部署」。

`@A`
### シナリオ: 所属部署に申請を作成すると Draft になる

* もし alice が sales 宛ての申請を作成する
* ならば 申請の状態は "Draft" になる
* かつ 申請は次の JSON と一致する:
  ```json
  {
    "author": "alice",
    "department": "sales",
    "status": "Draft"
  }
  ```

`@A` `@R2`
### シナリオ: 所属していない部署には申請を作成できない

* もし dave が sales 宛ての申請を作成する
* ならば 操作は "NotAffiliated" として拒否される
* かつ 申請は存在しない

`@A`
### シナリオテンプレート: 兼務ユーザーでも申請先は 1 つに定まる

carol は 2 部署に所属するが、申請ごとに申請先部署は 1 つ。どちらの部署宛てにも作れる。

* もし carol が <部署> 宛ての申請を作成する
* ならば 申請の状態は "Draft" になる
* かつ 申請の申請先部署は <部署> である

#### 例:

  | 部署  |
  | ----- |
  | sales |
  | eng   |

## ルール: 閲覧できるのは申請先部署に所属するユーザーだけ (R1, R2)

閲覧は状態遷移を伴わない述語なので、状態を問わずに **誰が見えるか** だけを表で列挙する。
`carol` は sales の一般メンバーとして sales 宛ての申請を読めるが、`dave` は eng にしか所属していないので読めない。

`@R1` `@R2`
### シナリオテンプレート: 閲覧可否は所属のみで決まる

* 前提 alice が sales 宛ての申請を作成している
* ならば <ユーザー> は申請を<閲覧可否>

#### 例: 所属している (R1)

  | ユーザー | 閲覧可否 |
  | -------- | -------- |
  | alice    | 閲覧できる |
  | bob      | 閲覧できる |
  | carol    | 閲覧できる |

#### 例: 所属していない (R2)

  | ユーザー | 閲覧可否 |
  | -------- | -------- |
  | dave     | 閲覧できない |

## ルール: 編集できるのは、Draft/Returned の作成者本人か、Pending までの上長だけ (U1, U2, U3)

編集の可否は (実行者, 状態) の表で決まる。U1 は作成者本人の行、U2 は他のメンバー（`carol`）の行、
U3 は上長（`bob`）の行に対応する。終端状態では誰も編集できない。

`@U1` `@U2` `@U3`
### シナリオテンプレート: 編集可否の表

* 前提 alice が sales 宛ての申請を作成している
* かつ 申請の状態が <状態> である
* ならば <実行者> は申請を<編集可否>

#### 例: 作成者本人 alice (U1)

  | 状態     | 実行者 | 編集可否   |
  | -------- | ------ | ---------- |
  | Draft    | alice  | 編集できる |
  | Returned | alice  | 編集できる |
  | Pending  | alice  | 編集できない |
  | Approved | alice  | 編集できない |
  | Rejected | alice  | 編集できない |

#### 例: 同じ部署の他のメンバー carol (U2)

  | 状態     | 実行者 | 編集可否     |
  | -------- | ------ | ------------ |
  | Draft    | carol  | 編集できない |
  | Returned | carol  | 編集できない |
  | Pending  | carol  | 編集できない |

#### 例: 申請先部署の上長 bob (U3)

  | 状態     | 実行者 | 編集可否     |
  | -------- | ------ | ------------ |
  | Draft    | bob    | 編集できる   |
  | Returned | bob    | 編集できる   |
  | Pending  | bob    | 編集できる   |
  | Approved | bob    | 編集できない |
  | Rejected | bob    | 編集できない |

`@U1` `@U3`
### シナリオ: 編集しても状態は変わらない

* 前提 alice が sales 宛ての申請を作成している
* かつ 申請の状態が Pending である
* もし bob が申請を編集する
* ならば 申請の状態は "Pending" のままである
* しかし alice が申請を編集すると "NotManager" として拒否される

## ルール: 提出・再提出できるのは作成者本人だけ (C)

`@C`
### シナリオテンプレート: Draft と Returned から Pending へ

* 前提 alice が sales 宛ての申請を作成している
* かつ 申請の状態が <遷移前> である
* もし alice が申請を提出する
* ならば 申請の状態は "Pending" になる

#### 例:

  | 遷移前   |
  | -------- |
  | Draft    |
  | Returned |

`@C` `@U3`
### シナリオ: 上長であっても他人の申請は提出できない

bob は sales の上長として Draft を **編集** はできるが（U3）、**提出** は作成者だけの操作である。

* 前提 alice が sales 宛ての申請を作成している
* もし bob が申請を提出する
* ならば 操作は "NotAuthor" として拒否される
* かつ 申請の状態は "Draft" のままである

## ルール: 決裁（承認・却下・差し戻し）できるのは Pending の申請に対する申請先部署の上長だけ (D, E, F)

3 つの決裁操作は事前条件が同じで、事後の状態だけが異なる。

`@D` `@E` `@F`
### シナリオテンプレート: 上長の決裁で状態が遷移する

* 前提 alice が sales 宛ての申請を作成している
* かつ 申請の状態が Pending である
* もし bob が申請を<操作>する
* ならば 申請の状態は "<遷移後>" になる
* かつ 申請の決裁者は bob である

#### 例:

  | 操作     | 遷移後   |
  | -------- | -------- |
  | 承認     | Approved |
  | 却下     | Rejected |
  | 差し戻し | Returned |

`@D` `@E` `@F`
### シナリオテンプレート: Pending でない申請は決裁できない

* 前提 alice が sales 宛ての申請を作成している
* かつ 申請の状態が <状態> である
* もし bob が申請を<操作>する
* ならば 操作は "WrongState" として拒否される
* かつ 申請の状態は "<状態>" のままである

#### 例:

  | 状態     | 操作     |
  | -------- | -------- |
  | Draft    | 承認     |
  | Draft    | 却下     |
  | Draft    | 差し戻し |
  | Returned | 承認     |
  | Returned | 却下     |
  | Returned | 差し戻し |

`@D` `@self-approval`
### シナリオ: 自己決裁は許可される

`spec.md` §4-D の注記。実行者が作成者本人であっても、申請先部署の上長なら承認できる。
これは P1 と矛盾しない——どちらも「承認可否は申請先部署での役職のみで決まる」という同じ規則の帰結である。

* 前提 bob が sales 宛ての申請を作成している
* かつ 申請の状態が Pending である
* もし bob が申請を承認する
* ならば 申請の状態は "Approved" になる
* かつ 申請の決裁者は bob である

## ルール: P1 兼務ユーザーの権限分離 — 承認可否は申請先部署での役職のみで決まる

carol は eng の `Manager` だが、sales では `Member`。sales 宛ての申請を、eng での上長権限を根拠に
決裁できてはならない。自分が作成した申請であっても同じ。

`@P1`
### シナリオテンプレート: 他部署の上長権限では決裁できない

* 前提 carol が sales 宛ての申請を作成している
* かつ 申請の状態が Pending である
* もし carol が申請を<操作>する
* ならば 操作は "NotManager" として拒否される
* かつ 申請の状態は "Pending" のままである

#### 例:

  | 操作     |
  | -------- |
  | 承認     |
  | 却下     |
  | 差し戻し |

`@P1`
### シナリオ: 同じ人物でも申請先が eng なら決裁できる

P1 の裏側。権限は人ではなく (ユーザー, 部署) に付くので、eng 宛ての申請なら carol は上長として承認できる。

* 前提 dave が eng 宛ての申請を作成している
* かつ 申請の状態が Pending である
* もし carol が申請を承認する
* ならば 申請の状態は "Approved" になる
* かつ 申請の決裁者は carol である

`@P1` `@R2`
### シナリオ: 所属していない部署の申請には一切触れない

dave は sales に所属しないので、閲覧できないだけでなく（R2）、どの操作も「申請が見えない」扱いで拒否される。

* 前提 alice が sales 宛ての申請を作成している
* かつ 申請の状態が Pending である
* もし 次の操作を順に試みる:
  | 実行者 | 操作     |
  | ------ | -------- |
  | dave   | 承認     |
  | dave   | 却下     |
  | dave   | 差し戻し |
  | dave   | 編集     |
  | dave   | 提出     |
* ならば すべての操作は "NotAffiliated" として拒否される
* かつ 申請の状態は "Pending" のままである

## ルール: P2 終端状態の不変性 — Approved / Rejected からは遷移しない

`@P2`
### シナリオテンプレート: 終端状態の申請にはどの操作も効かない

権限のある上長（bob）であっても、作成者本人（alice）であっても、他部署の上長（carol）であっても同じ。

* 前提 alice が sales 宛ての申請を作成している
* かつ 申請の状態が <終端状態> である
* もし 次の操作を順に試みる:
  | 実行者 | 操作     |
  | ------ | -------- |
  | bob    | 承認     |
  | bob    | 却下     |
  | bob    | 差し戻し |
  | bob    | 編集     |
  | alice  | 提出     |
  | alice  | 編集     |
  | carol  | 承認     |
* ならば すべての操作は "TerminalRequest" として拒否される
* かつ 申請は変化しない

#### 例:

  | 終端状態 |
  | -------- |
  | Approved |
  | Rejected |

## ルール: P3 迷子申請の不在 — どの申請にも決裁できる上長が少なくとも 1 人いる

「各部署に上長が 1 名以上」は名簿の不変条件（背景で確認済み）で、P3 はその帰結である。
申請先部署が名簿の部署である限り、その部署の上長が決裁者になる。

`@P3`
### シナリオテンプレート: 申請先部署ごとに決裁者が存在する

* 前提 <作成者> が <部署> 宛ての申請を作成している
* かつ 申請の状態が Pending である
* ならば 申請を決裁できるユーザーが少なくとも 1 人存在する
* かつ 申請を決裁できるユーザーは <決裁者> である

#### 例:

  | 作成者 | 部署  | 決裁者 |
  | ------ | ----- | ------ |
  | alice  | sales | bob    |
  | dave   | eng   | carol  |

`@P3`
### シナリオ: 上長のいない部署を許すと迷子申請が生まれる

P3 が名簿の不変条件に **依存している** ことを示す反例。bob を外した名簿は不変条件に違反し、
そのまま受け入れれば alice の申請は誰にも決裁できなくなる。

* 前提 名簿から bob を外す
* ならば 名簿は不変条件「各部署に上長が 1 名以上」に違反する
* しかし 不変条件を無視して alice が sales 宛ての申請を作成し Pending にすると、申請を決裁できるユーザーは存在しない

## ルール: 一連の操作 — 差し戻しから再提出、承認までの往復

個々の遷移ではなく **実行履歴** としての仕様。差し戻し（F）→ 再提出（C）→ 承認（D）を 1 本の
シナリオで追い、履歴の全体を固定する。

`@A` `@C` `@D` `@F`
### シナリオ: 往復して最終的に承認される

* 前提 alice が sales 宛ての申請を作成している
* もし 次の操作を順に試みる:
  | 実行者 | 操作     |
  | ------ | -------- |
  | alice  | 提出     |
  | bob    | 差し戻し |
  | alice  | 編集     |
  | alice  | 提出     |
  | bob    | 承認     |
* ならば すべての操作は成功する
* かつ 申請の状態は "Approved" になる
* かつ 履歴は次の通りである:
  ```
  Draft --alice:提出--> Pending
  Pending --bob:差し戻し--> Returned
  Returned --alice:編集--> Returned
  Returned --alice:提出--> Pending
  Pending --bob:承認--> Approved
  ```
